# cast-protocol-testkit

**投屏协议专项测试工具集 · 面向智能投影仪的互通、体验与异常恢复验证**

围绕 **AirPlay / DLNA（UPnP AV）/ Miracast**，规划 iOS、Android 测试工具与 Python 自动化能力，沉淀协议理解、风险驱动用例、指标测量、问题定位和质量结论。

> **当前阶段：规划与方案设计。** 本仓库目前只有文档，没有 App、自动化代码、可安装包或实测结果。文档中的功能、自动化方式和实验均为拟实施方案；设备支持范围、性能基线和验收阈值待确认。更新日期：2026-11-06。

## 项目目标

- **验证互通能力**：明确发送端、接收端、系统与接收软件版本，以及媒体、网络和权限前置条件。
- **复现异常场景**：围绕发现、建链、媒体访问、播放和恢复过程设计可控实验。
- **建立可解释的结果**：将操作、应用事件、媒体请求、设备日志和实际画面关联成证据包。
- **支撑质量判断**：给出已测范围、失败与阻塞项、未测风险和候选版本结论。

项目以系统公开能力和可获得的测试条件为基础。第三方接收实现、系统权限和产品声明都会影响覆盖范围；本项目不宣称协议认证或商业产品验收资质。

## 模块分工与当前状态

| 模块 | 计划能力 | 当前状态 / 边界 |
| --- | --- | --- |
| iOS AirPlay 测试端 | 标准媒体播放、系统媒体路由选择、播放控制、公开事件记录、镜像测试画面 | 待实现；系统屏幕镜像先由人工操作控制中心；不承诺完整握手信令 |
| Android DLNA 测试端 | UPnP AV 设备发现、描述解析、能力探测、播放控制、协议请求与响应记录 | 待实现；按接收端实际服务与动作能力适配，不假定 SDK 自带完整 DLNA 栈 |
| Android Miracast 辅助测试 | 已确认支持机型的系统操作辅助、帧号与旋转测试画面、结果与证据关联 | 待实现；依赖设备系统支持，不自行实现完整 Miracast 协议栈 |
| Python 自动化 | 可控 HTTP 媒体源、场景编排、故障注入、采集、结果汇总和报告 | 待实现；先以 DLNA 建立可执行闭环，再扩展人工与自动混合流程 |

真实投影画面是首帧、卡顿和镜像延迟的关键证据。应用端“正在播放”、SOAP 成功响应或系统路由切换，只能分别证明相应阶段，不能单独代表投屏成功。

## 第一阶段计划交付

1. 设备与接收方案能力矩阵、实验拓扑和风险驱动用例。
2. DLNA 的发现 → 控制 → 媒体请求 → 实际出画 → 报告闭环。
3. iOS AirPlay 最小测试端，以及 AirPlay / Miracast 镜像的人工辅助流程。
4. 可重复执行的异常恢复实验、统一证据包及问题定位记录。
5. 一份真实测试报告和一页质量结论；结果必须注明样本量、条件及限制。

**首个演示场景（待实施）**：正常播放建立基线 → 将媒体地址配置为可控 HTTP 错误 → 区分发现/控制成功与媒体请求失败 → 恢复资源并回归 → 自动汇总证据和结论。该场景属于实验故障注入，不代表已发现产品缺陷。

## 测试设计原则

- 按具体机型、固件、接收 App 和内容策略确认能力，不将“Android / iOS 支持”泛化为所有设备支持。
- 分清控制路径与媒体路径；手机作为本地媒体服务器和外部服务器供流分别设计用例。
- 标明公开 API 可见信息、外部测量信息与暂不可获得的信息。
- 用例结果与执行方式分开记录；未执行、阻塞、不适用不计为通过。
- 性能目标先形成测量口径与基线，再确定项目阈值；不预设某协议必然更快或更稳定。
- 抓包、日志与实物测量的覆盖条件需记录；模拟结果与真机结果分别报告。

更多设计见[测试策略](docs/测试策略.md)、[指标测量方法](docs/指标测量方法.md)和[质量门禁](docs/质量门禁.md)。
