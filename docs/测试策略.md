# 投屏专项测试策略

更新日期：2026-11-06。当前仅有规划；尚无实现、实测数据或已确认的测试设备。

本文用于确定先测什么、怎样形成证据及如何解释结果。项目定位见 [README](../README.md)，协议边界见 [协议对比](协议原理对比.md)，组件职责见 [架构设计](架构设计.md)。本文属于个人项目方案，不代表任何企业的测试规范。

## 1. 先确认能力，再选择用例

正式执行前填写 [能力矩阵](设备能力矩阵.md)：发送端型号和系统、接收端型号和固件、接收软件版本、支持的协议与模式、网络拓扑、可获得的日志权限。未确认的能力标为“待验证”，不能按设备品牌或系统名称推定支持。

分别识别媒体来源与传输路径：远程媒体 URL、本地媒体经 HTTP 提供、实时屏幕镜像。手机退后台、断网或退出后的预期，应结合源文件位置、服务存活、缓存及系统策略确定。受保护内容另设前置条件，不将所有黑屏都判定为缺陷。

本期范围以 Android DLNA 控制流程、iOS AirPlay 公开 API 可观测事件、Miracast 系统辅助测试为主。协议覆盖不等于全部流程自动化；暂不承诺私有握手解析、绕过系统交互或通用 DRM 验证。

## 2. 按用户风险安排优先级

优先级分配到每条用例，不按“功能/性能”章节整体定级。具体条目见 [测试用例](分协议测试用例清单.md)。

| 级别 | 选择原则 | 示例 |
| --- | --- | --- |
| P0 | 已支持场景的核心路径失效，或异常后无法恢复使用 | 发现并选择设备、开始播放或镜像、主动结束、失败后重新连接 |
| P1 | 常见体验、兼容性与恢复风险 | Seek、锁屏/后台、旋转、网络恢复、首帧和音画同步测量 |
| P2 | 扩展组合、探索与压力边界 | 特殊字符、更多媒体参数组合、额外设备或网络拓扑 |

同一场景可随产品定位升级优先级。例如面向会议演示时，镜像延迟可能属于高优先级。调整须记录理由，不能因实现困难降低等级。

## 3. 用最少设备建立可信闭环

先选一条已确认支持的端到端路径，完成正常播放、停止及一个可控异常，再扩大组合。设备不足时保留覆盖空白，不用模拟结果代替真实设备结果。兼容性选择以用户场景、系统版本变化、接收实现差异和已有失败记录为依据，不追求排列组合数量。

Python 媒体服务与编排优先落地，提供可控媒体、执行记录和报告汇总；Android DLNA 作为首个完整闭环。iOS 保留系统路由选择等必要人工步骤；Miracast 使用设备支持的系统入口及测试画面。能采集应用事件不代表已观测接收端出画。

## 4. 执行入口与产物

当前入口是本文、能力矩阵及用例文档；暂无可运行命令。后续执行器入口和参数应在实现后补充至 README。

每次执行先固定设备/固件、网络、媒体标识、用例版本及预期，再生成运行标识。记录执行方式（自动/人工/混合）、操作时间线、应用与可获得的接收端日志、媒体请求记录和必要视频；测量遵循 [测量方法](指标测量方法.md)。

用例结果统一为 `PASS`、`FAIL`、`BLOCKED`、`NOT_RUN`、`NOT_APPLICABLE`；当前默认 `NOT_RUN`。不适用必须说明能力或条件依据。报告分别列出计划、实际执行、阻塞及未执行数量，并写清成功率和覆盖率分母。

产物采用 [测试报告模板](模板/测试报告模板.md)；异常按 [排查框架](投屏问题排查框架.md) 和 [问题调查模板](模板/问题定位记录模板.md) 记录。未知根因保持“待定位”，区分事实、假设和证据缺口。

## 5. 本阶段完成标准

规划阶段要求范围、风险、能力边界、用例入口和测量口径相互一致。具备设备后，至少形成一条可重复执行路径、一份可追溯报告及一个异常调查记录，才可声明完成 MVP 验证。是否建议进入下一阶段，按 [质量门禁](质量门禁.md) 判断；实现顺序见 [路线图](项目路线图.md)。
