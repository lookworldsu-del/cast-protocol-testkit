# 投屏问题排查框架

更新日期：2026-11-06。本文是计划采用的排查方法，不包含实测案例、根因结论或已实现的采集能力。以下场景用于设计采集与复现流程，待设备、权限和工具验证后执行。

## 1. 一条记录保留五种信息

| 信息 | 记录要求 |
|---|---|
| 观察 | 用户操作和实际现象，写清起止事件、模式、发生次数与总次数 |
| 假设 | 按网络、发现、会话、媒体、显示分别列出可能原因 |
| 证据 | 原始日志、请求响应、画面录像及可重复的对照实验，关联采集位置和时间 |
| 未知 | 缺失的权限、链路、系统内部状态和无法解密的数据，明确不能推出什么 |
| 回归 | 保留失败条件，验证修复、邻近场景和未修改版本的差异 |

记录统一使用[问题定位记录模板](模板/问题定位记录模板.md)。每次运行拟关联用例编号、运行编号、手机型号与系统、接收端型号及固件/接收应用版本、协议模式、媒体参数和资源位置、网络拓扑、权限状态。尚未确认的信息标为“待确认”，不根据产品名称猜测。

App 日志、媒体服务器访问日志、路由器抓包、ADB/接收端日志和外部录像分别注明“可获得、待验证、不可获得”。普通 App 无法读取的系统内部状态，不承诺通过日志面板补齐。跨设备事件需说明时钟对齐方法；实际首帧与延迟依照[指标测量方法](指标测量方法.md)确认。

## 2. 五类场景的证据路径

### 2.1 发现不到接收端

**观察：** 区分系统列表没有设备、App 发现没有结果、设备出现后过期三种现象，记录搜索窗口与重试次数。

**假设与采集：** 先核对目标是否支持该协议及所需模式，再看接收服务开关、网络权限、SSID/VLAN、AP 隔离和组播策略。DLNA 拟采集 M-SEARCH、响应及设备描述 GET；AirPlay 比较系统路由界面与可获得的 Bonjour 观察；Miracast 比较系统投屏入口与 P2P 状态。分别证明“发出、到达、回复、展示”，避免仅凭同一 Wi-Fi 名称认定互通。

**未知与回归：** 抓包位置未覆盖 P2P 或交换路径时，“未抓到”不能证明未发送。用无隔离的基线网络作对照；跨 VLAN 记录发现代理和访问规则；peer-to-peer 仅在确认支持的设备上单列测试。

### 2.2 控制成功但不出画

**观察：** 将 SOAP 成功、播放器状态改变和投影实际出画分开记录。

**假设与采集：** DLNA 核对 URL 是否能从接收端网络访问、资源是否来自手机，检查 HTTP GET、状态码、Content-Type、Range/分段请求及传输中断；再对照编码、封装、分辨率和接收端能力。镜像则区分会话建立、媒体到达与显示输出，只有取得对应日志或抓包才能确认具体阶段。

**未知与回归：** 源端回调不能证明接收端已解码。用已知未保护的低复杂度素材、独立内容服务器和另一接收端逐项对照；输出根因前保留“网络可达/解码/显示仍待区分”等未知项。

### 2.3 Seek 失败或位置不一致

**观察：** 记录目标时间、响应、实际落点、恢复播放耗时，区分被拒绝、响应成功但未跳转、跳转后卡住。

**假设与采集：** 先核查当前内容是否可 Seek、动作与参数是否受支持，再关联 SOAP 响应、播放状态、媒体服务器后续请求及画面。直播、不可定位资源与可定位文件分开；HTTP 范围请求和关键帧可能影响行为，但不能凭现象直接认定某一原因。镜像中手机播放器 Seek 与 DMR 的远程 Seek 分属不同测试路径。

**未知与回归：** 接口返回的位置不等于可见画面的精确落点。保持媒体一致，比较开始、中间、末尾以及暂停状态下的操作；容差须先定义。

### 2.4 受保护内容黑屏

**观察：** 记录内容来源、App、协议模式、声音/字幕/界面是否仍可见，避免只写“DRM 不兼容”。

**假设与采集：** 先确认内容方是否允许该输出方式，再核对源端、接收端及下游显示链路的内容保护能力。仅在合法可获得时记录保护错误和协商日志；不得把 HDCP 链路保护、内容授权和格式解码混为一项。

**未知与回归：** 黑屏可能符合内容策略，不能据此归咎第三方接收方案。使用未保护素材作对照，再按明确授权的内容与预期测试；无授权素材或诊断条件时标记“未执行”。

### 2.5 断网、重启后无法恢复

**观察：** 写清被中断的是手机、内容服务器、AP 还是接收端；区分连接 AP 的 Wi-Fi 与 Miracast P2P 链路。

**假设与采集：** 拟关联中断前后发现缓存、IP/URL 变化、请求超时、服务重启及播放状态。DLNA 单列手机兼任内容源的拓扑；有条件时记录设备离线通知、重新发现及新会话，防止把旧 UI 状态当成功恢复。

**未知与回归：** 不默认必须无感续播；自动恢复、用户重连及超时提示须依据产品要求选择预期。比较短断网、长断网、冷启动和反复恢复，恢复成功仍需实际出画与控制可用的证据。

## 3. 收敛结论与提交修复验证

每轮只改变一个关键变量，先复现再增加观测。记录能够支持的最窄结论，例如“该拓扑下接收端未请求媒体”，不要直接升级为“接收端协议错误”。对接修复方时提交最小复现步骤、原始证据、影响范围、未排除项与回归条件，修复归属随证据更新。
