# 实施路线图

更新日期：2026-11-06。当前是规划仓库，没有应用代码、测试执行器、实测结果或已确认设备。

本文将 [项目定位](../README.md) 转化为可检查的实施阶段。以下“四周”仅是在具备可用设备和开发环境时的参考工作量分配，不是交付日期承诺。缺少接收端、平台权限或实际支持能力时，应调整范围并保留阻塞记录。

## 参考推进顺序

| 阶段 | 工作重点与执行入口 | 预期产物 | 完成标准 |
| --- | --- | --- | --- |
| 第 1 周：确认范围 | 根据 [协议对比](协议原理对比.md) 与 [能力矩阵](设备能力矩阵.md) 核实设备；细化 [测试策略](测试策略.md) | 一条可执行拓扑、风险清单、首批用例及测量口径 | 每个入选用例有前置条件、观察点和判定依据；未知能力不写成已支持 |
| 第 2 周：DLNA 闭环 | 按 [架构设计](架构设计.md) 先做 Python 可控媒体源，再做 Android 发现、控制及记录 | 正常播放到停止的记录、媒体请求日志、首份报告；至少一个可控异常 | 可重复执行并关联同一次运行的操作、请求及结果，失败时不会无期限等待 |
| 第 3 周：双端与镜像辅助 | 增加 iOS AirPlay 公开 API 测试页；确认设备上的 Miracast 系统入口及测试画面 | 可人工辅助的操作流程、应用事件记录、镜像测量样例 | 标明人工步骤和观察边界；不把播放器状态当作投影画面证据 |
| 第 4 周：复现与呈现 | 按 [用例](分协议测试用例清单.md) 执行小范围回归；整理异常、长稳观察与限制 | 实测报告、问题调查、演示材料和质量结论 | 数据可追溯，未测项完整列出，另一位使用者可按说明复现主要流程 |

各阶段引用 [测量方法](指标测量方法.md) 规定统计口径；报告与调查分别使用 [测试报告模板](模板/测试报告模板.md)、[问题调查模板](模板/问题定位记录模板.md)，定位流程见 [排查框架](投屏问题排查框架.md)。当前以上均为待实现或待验证产物。

## 范围取舍

优先保证一个真实接收端的 DLNA 控制、媒体请求、异常和报告闭环，再扩展设备与参数。iOS 的系统交互和 Miracast 的系统能力保留明确人工边界；没有足够设备时不以更多界面代替验证。

本期不增加独立 Java 后台、云设备平台或自研接收端。Google Cast、授权条件具备后的受保护内容验证、更多设备适配及更长稳定性观察属于后续候选；只有当前闭环通过 [质量门禁](质量门禁.md) 后再排序。配置长时间运行能力与实际完成长稳验证必须分开描述。

## MVP 的验收方式

从 README 的执行说明开始，选择已确认路径，完成一次正常流程和一次可控异常，生成包含环境、媒体、步骤、证据及结论的报告。若异常无法归因，交付证据和后续验证方案即可，不编造根因或修复记录。

MVP 完成意味着一个受限但可复现的验证闭环，不意味着协议认证、量产验收、全机型兼容或全天候稳定。没有真实执行证据前，项目保持“规划阶段”。
