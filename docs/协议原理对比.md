# AirPlay / DLNA / Miracast 协议原理对比

更新日期：2026-11-06。本文为 `cast-protocol-testkit` 的设计依据；项目当前只有规划，没有已实现模块、实测结果或已确认的设备支持清单。协议能力与具体产品支持范围分别记录，后者以[设备能力矩阵](设备能力矩阵.md)为准。

## 1. 先区分媒体播放与屏幕镜像

| 维度 | DLNA / UPnP AV 常见投送场景 | Miracast | AirPlay |
|---|---|---|---|
| 主要模型 | 控制器指定资源，渲染器获取并播放媒体 | 无线显示，会话协商后传输音视频 | 支持媒体播放和屏幕镜像，须分模式测试 |
| 发现与连接 | SSDP、设备描述、服务控制 | 常见为 Wi-Fi Direct；另有基础设施连接能力 | Bonjour，也存在特定设备的其他发现方式 |
| Android 测试端 | 规划实现 UPnP 控制器，需自行集成协议能力 | 借助支持该能力的系统投屏入口 | 本项目暂不规划 Android AirPlay 发送实现 |
| iOS 测试端 | 本项目暂不规划 | 不提供通用原生 Miracast 发送能力 | 规划调用公开播放与路由 API，镜像由用户在系统中启动 |
| 核心验证 | 资源可达、格式、控制动作与实际播放一致性 | 建链、首帧、镜像延迟、音画同步与恢复 | 模式、系统与接收端兼容性、首帧和恢复 |

这不是三种协议完整规范的等价比较。媒体播放同样存在启动耗时、控制响应和卡顿；控制信令少也不意味着媒体链路带宽占用低。不能脱离设备、媒体和网络条件预设哪种协议必然更快或更稳定。

## 2. DLNA：把控制与内容传输画清楚

常见场景包含 DMC（控制器）、DMS（媒体服务器）、DMR（媒体渲染器）。UPnP AV 规范使用 control point、MediaServer、MediaRenderer 描述相应角色；DLNA 还包含互操作约束，完成几个 UPnP 动作不等于通过 DLNA 认证。[UPnP AV 架构](https://upnp.org/specs/av/UPnP-av-AVArchitecture-v2.pdf)定义了这些角色及组合。

本项目拟先覆盖 HTTP 拉流路径：控制器通过 SSDP 搜索，读取设备与服务描述，调用 `SetAVTransportURI`、`Play`；渲染器向媒体 URL 发起 HTTP GET。SSDP 搜索通常为 UDP 组播，请求目标为 `239.255.255.250:1900`，响应为单播，不能写成广播发现。[设备架构规范](https://upnp.org/specs/arch/UPnP-arch-DeviceArchitecture-v2.0.pdf)给出了相应规则。

`AVTransport` 负责播放流程，`RenderingControl` 负责音量、静音等呈现属性，`ConnectionManager` 可查询协议与格式能力。动作是否支持要结合服务描述、当前状态及实际响应判断，不能要求所有接收端支持任意 Seek。SOAP 成功只表示控制请求被处理，仍需核验媒体请求和画面。[AVTransport 规范](https://upnp.org/specs/av/UPnP-av-AVTransport-v1-Service.pdf)说明了 URI 与 HTTP 获取的关系。

必须分别测试两种拓扑：媒体由独立服务器提供；手机同时充当控制器和本地 HTTP 内容源。由此可以推导：手机断网或进程结束时，前者可能继续播放，后者可能因内容源不可达而停止，缓存也可能延迟故障出现。Android 端需实现或集成 UDP、HTTP、XML 等能力，不能将其表述为调用现成的系统 DLNA 栈。

## 3. Miracast：P2P 网络不是完整投屏栈

公开的 `WifiP2pManager` 提供发现、连接与组网，不会自动完成无线显示。Miracast 还需要 RTSP 会话与能力协商、媒体编码传输及接收显示；控制链路与媒体链路要分别观察。[Android P2P 文档](https://developer.android.com/develop/connectivity/wifi/wifip2p)与[Wi-Fi Alliance 技术概览](https://tools.barco.com/kb-downloads/4814/Wi-Fi_CERTIFIED_Miracast_Technical_Overview_20170725.pdf)可对照阅读，后者为联盟原文、由 Barco 托管。

AOSP 的 Wi-Fi Display 扫描、连接接口带有 `@hide`，还受专用权限控制。因此普通 App 不承诺通用的一键连接、编码参数设置或完整协商日志。规划方案为：提供动态测试画面与音视频素材，辅助打开系统入口，再由外部观测确认投影效果。[AOSP 接口](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/hardware/display/DisplayManager.java)及[权限定义](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/res/AndroidManifest.xml)说明了边界。

基础设施连接须确认双方能力和具体扩展实现，不能默认任意 Android 与接收端支持。Miracast 可使用 HDCP；受保护内容能否显示还取决于内容策略和协商结果，黑屏不必然是缺陷。[Microsoft 的设备要求](https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/wireless-projection-pc-manufacturers)给出了受保护内容的相关条件。

## 4. AirPlay：系统能力与 App 可见范围分开

规划以 `AVPlayer` 播放测试媒体、`AVRoutePickerView` 让用户选择接收端，记录公开播放状态及错误。屏幕镜像由用户在控制中心启动；测试 App 只提供内容和观测辅助，不能把播放器路由选择等同于启动系统镜像。[路由组件](https://developer.apple.com/documentation/avkit/avroutepickerview)及[Apple 使用说明](https://support.apple.com/en-ca/102661)分别描述了两种操作。

公开状态不是全部协议握手日志，外部播放激活也不能证明投影已出画。媒体传输和保护行为不能直接等同 DLNA；须按实际模式、资源及接收端验证。局域网 Bonjour 是常见路径，但部分 Apple 设备支持 peer-to-peer AirPlay 等方式，不能将“无路由器必定不可用”推广到所有设备。[Apple 部署说明](https://support.apple.com/en-gb/guide/deployment/-dep9151c4ace/web)明确列出这些例外。

跨 VLAN 也不是统一的“不支持”：默认发现、发现代理、路由和访问控制要分别验证；搜得到不代表后续媒体链路可达。
