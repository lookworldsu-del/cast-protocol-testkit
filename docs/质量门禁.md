# 质量门禁与结论模板

更新日期：2026-11-06。本文是 cast-protocol-testkit 的个人项目模板，不代表 Anker、ODM 或任何认证机构的标准。当前没有代码、实测基线及已确认设备，不能据此给出产品放行结论。

用途是在 [测试策略](测试策略.md) 和 [路线图](项目路线图.md) 之间提供检查规则；入口是本页检查项，产物是附在 [测试报告](模板/测试报告模板.md) 中的阶段结论。

## 1. 分阶段检查

| 门禁 | 必须具备的证据 | 不满足时的处理 |
| --- | --- | --- |
| 规划资料可用 | [README](../README.md)、[协议对比](协议原理对比.md)、[架构](架构设计.md) 的范围一致；[能力矩阵](设备能力矩阵.md) 区分确认与待验证 | 修正文档后再实施，不宣称已有测试能力 |
| 单次执行有效 | 设备与版本、网络拓扑、媒体标识、用例版本、操作步骤、时间线与观察证据齐全；采用 [测量方法](指标测量方法.md) 的口径 | 标为阻塞或补测；不得根据日志缺失推定通过 |
| MVP 可复现 | 至少一条真实路径和一个可控异常可重复；产物可对应同一运行；必要人工步骤写明 | 缩小声明范围并列出剩余工作 |
| 版本候选可评价 | 约定范围内用例完成，失败、阻塞、未测风险及回归结果明确 | 给出不建议或有条件进入下一阶段的理由 |

## 2. 阈值与结果规则

发现耗时、首帧、控制响应、镜像延迟、音画同步、恢复时间和稳定性时长的阈值均为**待确定**。先明确用户场景、计时起止、样本数、统计方式与测量误差，再结合实测基线和产品要求设定目标。不能将其他设备的经验值直接当作验收标准。

基线用于观察变化，不能单独证明体验合格。报告保留单次数据及失败样本，按需要给出分布或分位数，不仅展示均值；每项比率注明分子、分母和排除项。重复运行配置与已完成的运行次数、时长分开记录。

`PASS` 表示已执行且满足预先确定的预期；`FAIL` 表示有证据证明不满足；`BLOCKED` 表示前置条件或观察条件不足；`NOT_RUN` 表示未执行；`NOT_APPLICABLE` 需说明适用性依据。自动化程度不改变判定标准，未执行与不适用均不能计为通过。

对照 [测试用例](分协议测试用例清单.md) 按具体风险决定阻塞程度，不以数量抵消核心路径失败。受保护内容黑屏需先核对授权、能力和内容策略；调查过程见 [排查框架](投屏问题排查框架.md)，证据及待验证假设写入 [问题调查](模板/问题定位记录模板.md)。

## 3. 质量结论应包含什么

每次结论写明：评价对象及版本、已测范围、有效样本与证据链接、失败和未知项、用户影响、后续动作及复测条件。可使用“建议进入下一阶段”“满足条件后进入”“暂不建议进入”“证据不足，暂无法评价”。

未知根因不能写成供应商责任；环境不足不能写成产品通过。个人项目只能对已测范围作结论；真实产品的放行仍需相应负责人结合业务要求作出决策。本文完成标准是规则清楚且可追溯，实际门禁通过须等待实施和实测证据。
